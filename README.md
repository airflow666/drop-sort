# ВИТРИНКА — пазл-сортировка для Яндекс Игр

Отображаемое название в консоли:

| Витрина | Полное | Короткое |
| --- | --- | --- |
| Русская | **ВИТРИНКА — собери свою полку** | **ВИТРИНКА** |
| Англоязычная | **VITRINKA — fill your shelf** | **VITRINKA** |

Название — одно и то же слово в двух начертаниях, а не перевод. Игрок, увидевший
обложку в одной локали и игру в другой, узнаёт её сразу; переведённое имя
(«Showcase», «Display») разорвало бы эту связь и заодно потеряло бы уже
набранную узнаваемость.

Игрок сортирует коллекционные фигурки из блайнд-боксов по витринам. Ядро —
проверенная механика ball sort, но витрина одновременно служит полкой
коллекции: собранный сет уезжает в витрину, открывает редкие скины и растёт
вместе с игроком.

Реализация по [плану разработки](#соответствие-плану). Стек: TypeScript +
PixiJS 8 + Vite, генератор уровней на Python.

```bash
npm install
npm run dev          # localhost:5173, работает без SDK (режим заглушки)
npm test             # типы + юнит-тесты ядра + тесты солвера и пака
npm run build        # сборка в dist/
npm run zip          # dist → vitrinka.zip для загрузки в консоль
```

Все команды работают одинаково в Windows (CMD и PowerShell), macOS и Linux:
внешних утилит вроде `zip` и `rm` в них нет. Нужен только Node 18+ — и Python 3
для двух команд, которые трогают уровни (`npm test`, `npm run levels`);
интерпретатор ищется сам, включая вариант `py -3` из Windows. Собрать и
упаковать игру можно вообще без Python: пак уровней лежит в репозитории.

## Дизайн

### Каждый сезон — своя линейка персонажей

Шесть серий на одних и тех же восьми силуэтах, различающиеся только цветом,
стоят в коллекции как одна линейка в шести оттенках: открывать бокс новой серии
незачем, там лежит то же самое в другом цвете. Поэтому у каждого сезона **свои
восемь персонажей** — 48 разных фигурок вместо восьми
([`src/theme/shapes.ts`](src/theme/shapes.ts)):

| Сезон | Линейка | Персонажи |
| --- | --- | --- |
| 1 · НЕОН | аркада, глянцевый винил | робот, кассета, молния, сердце, диско, ракета, глитч, кристалл |
| 2 · ПЛЮШ | зверята, матовая ткань | мишка, зайка, котик, утёнок, лягушка, барашек, пятачок, совёнок |
| 3 · ХРОМ | механика, зеркальный металл | меха, шестерня, лампа, капсула, будильник, гайка, магнит, батарейка |
| 4 · ЛЕТО | фрукты, мокрый глянец | лимон, арбуз, вишня, ананас, клубника, кактус, ракушка, груша |
| 5 · КОСМОС | тела и техника, сильное свечение | планета, луна, звезда, комета, НЛО, спутник, туманность, астронавт |
| 6 · ДЕСЕРТ | сладкое, сахарная поверхность | пончик, кекс, эскимо, карамель, тортик, зефир, леденец, пудинг |

Материал — это не декор поверх, а параметры самих слоёв: у плюша блик почти
выключен (`spec: 0.18`, острого блика нет вовсе), у металла контраст и кромка
на максимуме, у космоса приглушённая поверхность и полуторное свечение вокруг.
Отсюда и разница на расстоянии: плюшевая серия не бликует, металлическая
слепит.

### Чейз — это отделка, а не оттенок

Четыре редкие фигурки каждой серии сделаны так же, как в настоящих
блайнд-боксах: у них своя **отделка** (`Finish`), а не просто другой цвет.

| Отделка | Как выглядит |
| --- | --- |
| холо | радужный перелив по диагонали корпуса |
| блёстки | искры с ореолом внутри пластика |
| прозрачная | корпус просвечивает, видна толщина стенки |
| металлик | полированная полоса с тёмным переломом — только у легендарок |

Отделка подписана и на карточке коллекции, и на экране открытия бокса: с
миниатюры 78 пикселей видно, что фигурка особенная, но не видно чем.

### Фигурки описаны кодом, а не нарисованы

Вся коллекция из 72 фигурок — это 48 описаний силуэта
([`src/theme/shapes.ts`](src/theme/shapes.ts)) плюс таблица базовых цветов
([`src/theme/seasons.ts`](src/theme/seasons.ts)); отрисовкой занимается
[`src/theme/figurines.ts`](src/theme/figurines.ts). SVG собирается в рантайме и
растеризуется в текстуру ровно в том разрешении, которое нужно устройству.

Почему не атласы: 72 фигурки в трёх плотностях — это несколько мегабайт PNG при
бюджете сборки 15 МБ и требовании стартовать за 5 секунд. Здесь на старте
растеризуются только 8 видов, которые реально выйдут на поле; остальные — когда
игрок открывает коллекцию.

Объём даётся слоями: запечённое свечение → контактная тень → корпус с
радиальным градиентом → внутренняя тень у основания → **контровой свет по
нижне-правому краю** → мягкий блик → острый блик → отделка чейза → детали →
лицо. Контровой свет здесь главный: без него фигурка читается как плоское
цветное пятно.

Все производные оттенки (светлый, тёмный, контровой, цвет глаз) вычисляются из
одного базового цвета формулой в [`src/theme/color.ts`](src/theme/color.ts).
72 набора оттенков, набранных вручную, неизбежно разъехались бы по светлоте.

Три приёма, без которых половина силуэтов выглядела бы кривой:

* **`soften`** — корпус дополнительно обводится собственным градиентом.
  Скругляет вершины у полигонов (молния, кристалл, гайка, звезда) и прячет
  стыки составных контуров. Без него молния выглядела вырезанной ножницами.
* **Толстая обводка вместо контура** там, где деталь — это «труба»: руки
  кактуса собраны из ломаной с круглыми стыками, а не из дуг. Контур из дуг
  расходился в местах соединения, и кактус выглядел собранным из обрезков.
* **Свечение обводкой для фигур с отверстием.** У пончика залитая размытая
  копия затягивала дырку — пончик переставал быть пончиком.

### На поле выходит то, что игрок сам выбрал

По умолчанию на поле стоят восемь обычных фигурок текущей серии. Любую из
восьми позиций игрок заменяет собранной фигуркой — чейзом или экземпляром из
прошлого сезона — одним тапом по карточке в витрине
(`Profile.fieldSpecies`). Повторный тап возвращает стандартную.

Замена **поштучная и по позиции**: у каждой серии свои персонажи, «котика» из
плюшевой линейки в космической просто не существует, а позиция есть всегда. На
поле поэтому всегда ровно восемь разных силуэтов.

Ключ выставленной фигурки проверяется при загрузке трижды — существует,
совпадает по позиции, собрана, — иначе сохранение от старой версии выставило бы
на поле два одинаковых силуэта.

### Вид кодируется формой, а не только цветом

В сортировках виды обычно различаются исключительно цветом — и игроки с
дальтонизмом (около 8% мужчин) в такую игру играть не могут вовсе. Здесь у
каждого из восьми видов серии свой силуэт, и это жёсткое ограничение при
наборе линейки: круглый, вытянутый, с ушами, с отверстием, лучевой, с хвостом,
широкий, угловатый.

Проверяется это не на глаз, а скриптом:

```bash
npm i -D playwright-core --no-save
npx tsx store/preview-figurines.ts                 # контрольный лист всех 72 фигурок
npx tsx store/preview-figurines.ts --grayscale     # то же в оттенках серого
```

Чёрно-белый лист — главная проверка линейки: если на нём два вида одного сезона
неразличимы, набор персонажей собран неправильно. Скрипт заодно ищет пары
видов, близкие **и** по тону, **и** по светлоте, — то есть настоящую путаницу,
а не формальное совпадение одного параметра.

### Ощущения

План прямо запрещает экономить на тактильности, поэтому:

* высота ноты при укладке фигурки растёт вместе с заполнением витрины — к
  четвёртой фигурке нота почти на октаву выше первой;
* закрытие витрины звучит как защёлкнувшееся стекло: два обертона плюс высокий
  шумовой призвук;
* фигурка летит к витрине по дуге, длительность и высота которой считаются от
  расстояния: соседняя витрина и витрина через весь экран не могут занимать
  одинаковое время, иначе короткий ход выглядит вялым, а длинный — рывком;
* в паз она входит с разгоном и приплюскивается при посадке — ощущение
  защёлкивания даёт удар о дно, а не промах мимо паза (кривая с перелётом
  здесь считала перелёт в долях всей высоты падения и роняла фигурку
  на десятки пикселей ниже дна витрины);
* поднятая фигурка покачивается «в руке»: без движения состояние «я её держу»
  ничем не отличается от «она просто нарисована выше»;
* точка касания отмечается расходящимся кольцом, закрытый сет — кольцом во всю
  витрину и осадкой шкафа вместе с содержимым;
* комбо считается **по номерам ходов**, а не по секундам: временное окно
  наказывало бы игрока за лаги на слабом устройстве;
* вибрация через Vibration API, ровно 12 мс на укладку.

Звук синтезируется через WebAudio ([`src/platform/audio.ts`](src/platform/audio.ts)),
а не грузится в OGG: ноль байт в сборке, ноль времени на декодирование и высота
тона, отвечающая на состояние игры.

## Архитектура

```
src/
  core/       правила сортировки, состояние поля, солвер подсказок
  levels/     пак уровней и его выдача режимам
  theme/      силуэты, материалы, палитры, сезоны, скины витрин
  render/     слой Pixi: витрины, фон, эффекты, твины
  ui/         интерфейс на DOM: HUD, экраны, диалоги
  meta/       профиль: прогресс, валюта, коллекция, стрик
  platform/   обёртка над Yandex SDK, часы площадки, рекламная политика, звук
  app.ts      машина состояний: экраны и режимы
tools/        генератор уровней и солвер (Python), упаковка архива (Node)
test/         юнит-тесты ядра
store/        материалы для карточки игры и смоук-тест
```

`core/` и `theme/` не знают о браузере вообще: у них отдельная конфигурация
типов ([`tsconfig.node.json`](tsconfig.node.json)) **без `lib.dom`**, так что
случайное обращение к `document` там не скомпилируется. Благодаря этому ядро
тестируется в чистом Node, без jsdom и без сборки.

Интерфейс сделан на DOM, а не на Pixi: русский текст в Pixi требует растровых
шрифтов (сотни килобайт и мыло на нестандартном DPR), а DOM рисует системным
шрифтом — ноль байт и идеальная резкость. Canvas отвечает только за игровое
поле и фон.

## Уровни

Уровни генерируются офлайн и вшиваются в бандл: в рантайме ноль вычислений.

```bash
npm run levels       # перегенерировать пак (около 15 секунд на 4 ядрах)
npm run test:levels  # проверить: каждый уровень решаем, minMoves точен
```

Схема: раздать фигурки случайно по рабочим витринам → точно решить
состояние A\* → оставить, только если оптимум попал в целевой коридор ходов
для этого участка кривой сложности.

Кривая пака (по ней он отсортирован при генерации):

| Участок | Уровни пака | Видов | Свободных витрин | Ходов |
| --- | --- | --- | --- | --- |
| intro | 1–20 | 3 | 2 | 10–12 |
| early | 21–80 | 4–5 | 2 | 13–19 |
| mid | 81–200 | 5–6 | 2 | 16–24 |
| late | 201–500 | 6–7 | 1–2 | 20–39 |
| expert | 501+ | 7–8 | 1 | 29–44 |

### Сложность в ленте гуляет, а не растёт по прямой

Сначала уровень n брался из пака строго по порядку. Пак отсортирован по кривой
выше, поэтому первые два десятка уровней шли подряд на трёх видах и пяти
витринах — игра читалась как застывшая.

Теперь номер уровня задаёт только **середину коридора**, а число видов гуляет
вокруг неё на ±1 (`speciesFor` в
[`src/levels/provider.ts`](src/levels/provider.ts)). Соседние уровни отличаются
на глаз, при этом общий подъём сохраняется, а каждый одиннадцатый уровень
по-прежнему разгрузочный. Ступени середины сжаты: 3 вида до 4-го уровня,
4 до 14-го, 5 до 30-го, 6 до 70-го, дальше 7. Восемь видов остаются редкостью —
в паке таких уровней всего одиннадцать.

Первые два уровня разброса не получают вовсе: по прохождению первого считается
метрика плана (§10), и оставлять её на волю генератора незачем.

### Виды раздаются по всей серии

В паке виды пронумерованы 0..n−1, поэтому уровень на три вида состоял из видов
0, 1 и 2 — то есть из первых трёх фигурок серии. За всю кампанию игрок видел их
постоянно, а восьмую фигурку — только в одиннадцати уровнях из пятисот двадцати.

Теперь номера переназначаются на случайное подмножество **всех восьми**:
три вида уровня могут оказаться хоть первым, четвёртым и восьмым. Замер по
первым тремстам уровням — каждый из восьми видов встречается 228–250 раз.

Кампания бесконечная: уровни сверх пака переиспользуются с другими видами и
порядком витрин. И раздача видов, и перестановка витрин — симметрии задачи, они
не меняют ни решаемость, ни минимальное число ходов, поэтому `minMoves`
остаётся точным без повторной прогонки солвера.

### Почему решаемость обеспечивает солвер, а не построение

План (§6) предлагал строить уровень обратными ходами от решённого состояния,
чтобы решаемость следовала из построения. Так не получается: в решённом
состоянии каждая витрина полна и однородна, то есть **закрыта стеклом**, и
обратное блуждание вынуждено сначала занять пустые витрины — а вернуть их в
пустое состояние оно уже не может. Замер: из 25 попыток нужное число пустых
витрин не дал ни один прогон.

Поэтому решаемость обеспечивает шаг 3, который план и так требовал: каждый
уровень пропускается через A\*, и в пак попадает только доказанно решаемый с
точным оптимумом. Цена — при одной свободной витрине случайная раздача решаема
примерно в 2% случаев, но нерешаемость распознаётся за ~2 мс, так что отбор
всё равно дешёвый.

### Правила в двух реализациях

`minMoves` считает Python ([`tools/sortlib.py`](tools/sortlib.py)), а играет
TypeScript ([`src/core/board.ts`](src/core/board.ts)). Если реализации разойдутся
хотя бы в одном краевом случае, `minMoves` во всех паках станет ложью, а три
звезды — недостижимыми.

Против этого есть перекрёстная проверка: `tools/test_generator.py` выгружает 50
состояний с эталонными списками допустимых ходов в `test/fixtures/parity.json`,
а тест ядра сверяет с ними `Board.canMove`, флаги закрытых витрин и условие
победы. Плюс A\* сверяется с полным обходом в ширину на 120 малых задачах, и
отдельно проверяется, что эвристика ни разу не переоценивает остаток (иначе
найденный «оптимум» был бы завышен).

## Монетизация

Вся реклама проходит через [`src/platform/ads.ts`](src/platform/ads.ts) —
единственную точку, откуда её вообще можно позвать. Слой сам останавливает
геймплей через `GameplayAPI`, глушит звук и показывает плашку отсчёта.

**Фулскрин** — только на переходе к следующему уровню, после того как игрок
увидел награду и сам нажал «дальше». Не перед экраном победы: перебивать
роликом момент награды — значит отдавать удержание за один показ.

Частоту держим на своей стороне: не чаще **раза в 100 секунд** и не чаще, чем
**раз в три перехода**, причём отсчёт стартует с запуска игры — первые полторы
минуты сессии проходят без фулскрина вовсе. Ролик за награду тоже отодвигает
следующий фулскрин: два ролика подряд ощущаются как один сплошной рекламный
блок, даже если первый игрок включил сам.

Одного лимита площадки для этого мало, хотя он есть: она не покажет фулскрин
чаще чем раз в 60 секунд (значение настраивается в консоли) и вернёт
`wasShown = false`. Но уровень в бесконечной ленте проходится секунд за
пятнадцать, и на каждом переходе игрок получал трёхсекундную плашку «Реклама
через 3, 2, 1», после которой ролика не было — площадка его отклоняла. Три
потерянные секунды на каждом уровне и ни одного показа. Теперь, если показывать
рано, отсчёт вообще не запускается и переход мгновенный.

**Rewarded** — шесть поводов: +1 свободная витрина (в тупике), отмена хода,
подсказка, ×2 к монетам, открытие блайнд-бокса, дополнительная попытка в блице.
Награда выдаётся **только** по событию `onRewarded`; начислять по `onClose` —
это платить за закрытый крестиком ролик, и рекламная сеть считает такое фродом.

«+1 витрина» предлагается ровно в тупике (`Board.isDeadlock`), а не по таймеру.
Предложение по таймеру игрок читает как навязчивую рекламу, в тупике — как
спасение. Пустая витрина при этом гарантированно расшивает любой тупик, что
проверено тестом.

### В соревновательных режимах преимущество за ролик не продаётся

Блиц и вызов дня отправляют результат в общую таблицу, поэтому там нет ни
свободной витрины, ни отмены хода, ни подсказки за просмотр
(`isCompetitive` в [`src/meta/profile.ts`](src/meta/profile.ts)):

| | Кампания | Вызов дня и блиц |
| --- | --- | --- |
| +1 витрина (rewarded) | да | **нет** |
| Отмена хода (rewarded) | да | **нет** |
| Подсказка за ролик | да | **нет** |
| Подсказка из накопленных зарядов | да | да |
| ×2 к монетам, попытка блица, бокс | да | да |

Причина прямая: вызов дня ранжируется по числу ходов, а отмена хода этот
счётчик уменьшает — тот, кто посмотрел три ролика, оказывался бы в таблице выше
того, кто честно решил задачу. Свободная витрина решает уровень за игрока, а
подсказка — это ход от солвера. Уже накопленные заряды тратить можно: они
появляются у всех одинаково и покупкой внимания не являются.

Кнопки в этих режимах не выключаются, а **убираются**: выключенная кнопка
читается как «пока недоступно» и заставляет искать условие, которого нет.
Поводы, не влияющие на результат (×2 к монетам, лишняя попытка блица, бокс),
остаются везде.

**Инапы** детерминированные: игрок заранее видит, что покупает. Случайные
блайнд-боксы открываются только за монеты, дубликаты и rewarded — **никогда за
реальные деньги**. Это и этическая позиция при молодой аудитории, и снижение
риска на модерации.

## Публикация в Яндекс Играх

1. **Сборка и архив**

   ```bash
   npm run zip     # соберёт dist/ и упакует в vitrinka.zip
   ```

   Команда работает одинаково в Windows (CMD и PowerShell), macOS и Linux:
   архив пишет [`tools/pack.mjs`](tools/pack.mjs) средствами самого Node, без
   `zip`, `rm` и `unzip`. Ничего доустанавливать не нужно.

   Она же печатает содержимое архива — там должно быть ровно три файла:
   `index.html`, один `.js` и один `.css`. Скрипт проверяет, что `index.html`
   лежит в корне (иначе площадка сборку не примет), и каждый раз создаёт архив
   заново.

   Двух граблей, на которые тут легко наступить, в этом пути нет:

   * консольный `zip` по умолчанию **дописывает** в существующий архив. Имена
     файлов сборки содержат хеш, поэтому старые не перезаписывались, а
     копились: в архиве оказывалось три копии игры вместо одной;
   * `Compress-Archive` из PowerShell 5.1 (версия по умолчанию в Windows)
     записывает во внутренние пути **обратные** слэши, и часть распаковщиков
     читает такой архив как один файл с длинным именем вместо дерева.

2. **Консоль разработчика.** На [games.yandex.ru/console](https://games.yandex.ru/console/)
   создайте черновик и загрузите архив.

3. **Лидерборды.** Создайте два с техническими именами, которые ждёт код
   ([`src/platform/ids.ts`](src/platform/ids.ts)):

   | Имя | Сортировка | Смысл |
   | --- | --- | --- |
   | `blitzWeekly` | больше — лучше | очки за забег в блице |
   | `dailyMoves` | **меньше — лучше** | ходов в ежедневном вызове |

   Имя лидерборда консоль принимает только по маске `[a-zA-Z0-9]` — без
   подчёркиваний и дефисов. Первые версии назывались `blitz_weekly` и
   `daily_moves`, и в форму они просто не вводились. Маску проверяет юнит-тест,
   так что следующее имя с подчёркиванием не доедет до консоли; у товаров
   ограничение мягче, там подчёркивания допустимы.

4. **Товары (внутриигровые покупки).** Код сам по себе не создаёт ни одного
   товара — он только запрашивает каталог у платформы. Пока товар не заведён в
   консоли, `getCatalog()` его не вернёт, и в магазине вместо цены будет
   прочерк на неактивной кнопке. Поэтому **каждый товар нужно завести вручную**
   в разделе «Монетизация → Внутриигровые покупки», и его идентификатор обязан
   совпадать посимвольно с константами в
   [`src/platform/ids.ts`](src/platform/ids.ts). Готовые значения полей формы —
   название, описание на двух языках, цена и иконка — лежат в
   [`store/CARD.md`](store/CARD.md), копируются оттуда как есть:

   | ID | Что выдаёт | Тип | Можно купить повторно |
   | --- | --- | --- | --- |
   | `hints_10` | +10 подсказок | расходуемый | да |
   | `week_pass` | 60 монет и подсказка каждый день, 7 дней | расходуемый | да, продлевает |
   | `no_ads` | отключает фулскрины и баннер | навсегда | нет |
   | `skin_chrome` | скин витрин «Хром» | навсегда | нет |

   У платформы нет отдельного флага «товар навсегда»: разница целиком на
   стороне игры и держится на `consumePurchase`. Расходуемый товар мы
   подтверждаем сразу после выдачи — и он снова доступен к покупке.
   Товар «навсегда» **не подтверждаем никогда**: непотреблённая покупка
   продолжает приходить в `getPurchases()` при каждом запуске, и это
   единственное, чем платформа помнит факт владения. Списки живут в
   `CONSUMABLE_PRODUCTS` ([`src/platform/ids.ts`](src/platform/ids.ts));
   добавляя расходуемый товар, впишите его туда, иначе купить его второй раз
   будет нельзя.

   Цену, название и описание задаёт консоль — игра показывает то, что пришло в
   каталоге, и подставляет свои тексты только пока каталог не ответил.
   Монетизацию нужно включить в настройках черновика и дождаться модерации
   товаров: до неё каталог приходит пустым и на боевой площадке.

   Покупки запрашиваются с `signed: false`
   ([`src/platform/sdk.ts`](src/platform/sdk.ts)) — проверять подпись было бы
   нечем, своего сервера у игры нет. Это осознанный размен: за деньги
   продаётся только косметика и удобства, ничего влияющего на лидерборды.
   Секретный ключ из консоли (вкладка «Инап-покупки → Настройки») нужен ровно
   для серверной проверки подписи, и в клиенте ему делать нечего: бандл виден
   игроку целиком. В репозитории его нет и быть не должно.

   **Проверку необработанных покупок нужно настроить ДО первой тестовой
   покупки.** Площадка называет её обязательной для модерации (п. 1.13.1) и
   предупреждает отдельно: если купить и протестировать товары раньше, чем
   настроено консумирование, останутся необработанные платежи, и модерацию
   пройти будет уже невозможно. В игре проверка есть с самого начала —
   `redeemPendingPurchases()` вызывается на каждом запуске из
   [`src/main.ts`](src/main.ts), — так что тестовые покупки можно делать сразу.

   ### Порядок выдачи покупки: сохранить, потом потребить

   `consumePurchase()` удаляет покупку безвозвратно, поэтому документация
   требует сначала записать данные игрока и только потом подтверждать платёж.
   Весь путь выдачи — один метод `grantAndConsume()`
   ([`src/app.ts`](src/app.ts)), общий и для покупки в магазине, и для
   необработанных платежей с прошлого запуска:

   1. выдать товар в профиль;
   2. **дождаться подтверждённой записи** — `setData` возвращает признак того,
      дошла ли она, а таймаут считается отказом, а не успехом;
   3. и только теперь `consumePurchase`.

   Если запись не дошла, платёж намеренно остаётся необработанным: он придёт в
   `getPurchases()` при следующем запуске, и товар выдастся тогда. Это штатное
   восстановление, ради которого проверка и существует.

   Обратный случай — запись прошла, а `consume` нет — закрыт реестром выданных
   платежей в сохранении (`appliedPurchases`). Без него один платёж выдал бы
   товар дважды: покупка снова придёт в списке, а профиль уже пополнен. В
   реестр попадают только расходуемые товары; нерасходуемые приходят в списке
   всегда, и их выдача идемпотентна по природе — флаг и множество скинов.

   Раньше здесь была ровно та ошибка, от которой предупреждает документация:
   `applyPurchase` ставил флаги в памяти (часть — с отложенной на 2,5 секунды
   записью), а `consume` улетал следующей строкой.

   ### Портальная валюта берётся у площадки

   Цена на кнопке — это `priceValue` и иконка валюты из `getPriceCurrencyImage`,
   то есть из свойств самого товара (п. 1.13.2). Своя нарисованная монетка была
   бы не мелочью: валюта различается по регионам, и нарисованный ян в турецкой
   витрине показывал бы игроку не ту цену, которую с него возьмут. Если иконки
   в каталоге нет, кнопка откатывается на строку `price`, где валюта уже
   вписана текстом.

5. **Медиаматериалы**

   ```bash
   npm i -D playwright-core --no-save
   npx tsx store/make-assets.ts        # иконка 512×512 и обложки 800×470 (ru + en)
   ```

   Иконка и обложка собираются из тех же фигурок и той же палитры, что и игра:
   нарисованные вручную материалы расходятся с билдом после первой правки
   палитры, и в витрине оказывается игра, которая выглядит иначе, чем на
   картинках.

   Обложка — единственный материал карточки с текстом, поэтому она своя на
   каждый язык: `cover-800x470-ru.png` и `cover-800x470-en.png`. Иконке локаль
   не нужна, текста на ней нет. Скрипт меряет колонку текста и ряд витрин и
   падает, если они сошлись ближе чем на 12 пикселей: английские строки на те
   же слова длиннее русских, и наехать на витрины они могли бы молча.

   Полный список материалов и полей консоли — в
   [`store/CARD.md`](store/CARD.md).

6. **Песочница.** Черновик доступен по ссылке
   `https://yandex.ru/games/app/<ID>/?draft=true` — там работает настоящий SDK.
   Индикатор в [debug-панели](https://yandex.ru/dev/games/doc/ru/console/debug-panel):
   `W` — SDK ещё не готов, `IT` — всё в порядке.

### Особенности хостинга, уже учтённые в сборке

Все три — в [`vite.config.ts`](vite.config.ts), и все три проявляются **только**
на реальном хостинге, а на localhost выглядят исправными:

* JS и CSS кладутся **в корень** `dist/`, без подпапки `assets/` — файлы из
  подпапки стабильно отдают 404 на хостинге Яндекса;
* с модульного скрипта снимается атрибут `crossorigin` — раздача с
  CDN-поддомена без CORS иначе молча блокирует выполнение модуля, и игра не
  запускается вообще;
* `modulePreload` отключён и все динамические импорты слиты в один файл — по
  той же причине;
* `/sdk.js` подключается программно из [`src/platform/sdk.ts`](src/platform/sdk.ts),
  а не тегом в разметке: устойчивее к строгому CSP и без гонки состояний.

## Два языка

Интерфейс существует на русском и английском. Язык **не выбирается в игре**: он
приходит от площадки через `ysdk.environment.i18n.lang` — это прямое требование
модерации (§2.14). Логика простая: `ru` — русский, пустой ответ — тоже русский
(основной рынок), всё остальное — английский. Игроку из турецкой витрины
английский текст понятнее русского.

Весь текст живёт в одном словаре ([`src/i18n/index.ts`](src/i18n/index.ts)) —
включая имена 48 силуэтов, 24 чейзов, названия сезонов и скинов. Русский
словарь объявлен через `as const` и служит источником типа ключей, а английский
обязан быть `Record<Key, string>`: **забытый перевод не собирается**, а не
показывает пустую строку на боевой площадке.

Строки не запекаются в данные. `FigurineDef` хранит силуэт и ключ варианта, а
не готовое имя; `Season` — номер, а не название. Причина простая: язык приходит
от площадки уже после того, как модули загрузились, и запечённое при импорте
имя осталось бы русским на английской витрине.

Тестами закрыто то, что типы поймать не могут: пустые строки, кириллица в
английском словаре и расхождение подстановок — шаблон с `{n}` в одном языке и
без него в другом компилируется прекрасно, а в игре даёт строку без числа.
Смоук-тест отдельно открывает игру с локалью `en-US` и проверяет, что в меню и
в коллекции (72 имени фигурок) не осталось ни одного кириллического символа.

Множественное число разное по устройству: русскому нужно три формы и правило по
последним двум цифрам, английскому — две. Разделитель разрядов тоже свой:
`1 240` против `1,240`.

### Название тоже переключается

Отображаемое имя игры живёт там же, где остальной текст: `BRAND` и ключ
`app.title` в [`src/i18n/index.ts`](src/i18n/index.ts). Заголовок вкладки
выставляется в рантайме (`document.title = t('app.title')`,
[`src/app.ts`](src/app.ts)), потому что язык приходит от площадки уже после
загрузки модулей — статический `<title>` в `index.html` остался бы русским на
англоязычной витрине. В консоли те же две строки нужно вписать руками, каждую
в свою языковую вкладку; они собраны в [`store/CARD.md`](store/CARD.md).

## Чек-лист модерации

Проверяется автоматически смоук-тестом (`node store/smoke.mjs`), где отмечено ✅.

* ✅ `LoadingAPI.ready()` — ровно один раз и последним шагом старта: смоук-тест
  снимает состояние экрана в момент вызова и требует, чтобы загрузчика на нём
  уже не было, а меню было собрано
* ✅ `GameplayAPI.start()/stop()` — на старте уровня, на паузе, на рекламе, при
  сворачивании вкладки и **на возврате в уровень после ролика** (подсказка,
  отмена хода и свободная витрина берутся посреди живой партии)
* ✅ `game_api_pause` / `game_api_resume` — подписка выставляется до загрузки
  ресурсов: полноэкранную рекламу на старте площадка показывает сама, без
  callback-ов, и поздняя подписка пропустила бы паузу
* Календарная мета считает время по `ysdk.serverTime()`, а не по часам
  устройства: награда за вход, недельный пропуск, вызов дня, смена сезона,
  восстановление попыток блица и таймер забега
* Оценка игры спрашивается через `feedback.canReview()` → `requestReview()`,
  один раз за сессию и только после удачи (три звезды, рекорд блица) — в меню,
  а не поверх карточки победы
* Кнопка «Назад» на пульте телевизора (`HISTORY_BACK`) открывает свой диалог с
  подтверждением, выход отправляется событием `EXIT`
* Запись сохранений держится в лимите площадки (100 обращений `setData` за 5
  минут): дебаунс 4 секунды, счётчик записей в окне и повтор после отказа
* ✅ **Ни одного запроса к внешним домменам**: уровни, шрифт (системный), звук
  (синтез) и графика (SVG в коде) — всё в бандле
* ✅ Реклама не показывается до начала игры и не появляется поверх активного
  геймплея
* ✅ Плашка «Реклама через 3, 2, 1» перед фулскрином — палец успевает уйти с
  экрана, случайного клика не будет
* ✅ Прогресс переживает перезагрузку (незаконченная партия сохраняется снимком)
* ✅ Строка HUD помещается в экран — проверяется по фактическим границам
  элементов в блице, самом плотном режиме
* ✅ Контекстное меню браузера выключено в игровой области (§1.6): на телефоне
  оно всплывало от долгого нажатия прямо посреди партии
* Награда за rewarded — только после события `onRewarded`
* Не требует авторизации и персональных данных: `getPlayer({ scopes: false })`,
  резерв на `localStorage`. Игра грузится архивом, поэтому `localStorage`
  оборачивает сам SDK — отдельный `getStorage()` не нужен
* ✅ Язык интерфейса определяется через `ysdk.environment.i18n.lang` (§2.14):
  русский и английский, переключателя внутри игры нет намеренно
* Звук глушится на рекламе и при сворачивании; кнопка звука в меню и в игре
* Все вызовы SDK в `try/catch` **и с таймаутами**: на части встраиваний промисы
  SDK не резолвятся вообще, и без таймаута игра нависла бы на загрузке
* Пауза обрабатывается и через события SDK, и через `visibilitychange` — второй
  канал работает всегда
* Возрастной рейтинг ставится по факту содержания; случайное содержимое за
  реальные деньги не продаётся

## Тесты

```bash
npm test                    # всё сразу
npm run test:core           # 73 юнит-теста: правила, солвер, оценка, часы, твины
npm run test:levels         # солвер, эвристика, все 840 уровней пака
node store/smoke.mjs        # 55 проверок в браузере (нужен npm run build), ~3 минуты
```

Смоук-тест ловит то, что не поймают ни типы, ни юнит-тесты: игра запускается из
бандла, доходит до меню, показывает вводный гайд перед первой партией и **не
показывает его во второй раз**, начинает уровень, реагирует на тапы по витринам,
проходит уровень до победы, показывает фулскрин ровно на переходе, отыгрывает
блиц, выставляет собранную фигурку на поле и не сыплет ошибками в консоль.
Автопрохождение идёт через тот же `BoardView.tap`, что и палец игрока, — то есть
проверяется настоящий путь ввода вместе с анимациями.

Отдельно проверяется состав панели инструментов: в кампании три кнопки, в блице
одна — так регресс в правиле «в лидербордных режимах преимущество за ролик не
продаётся» падает тестом, а не всплывает в таблице рекордов.

Смоук-тест нашёл две ошибки, которые больше нечем было поймать.

**Тапы не доходили до витрин.** HUD получал класс `.ui` с `inset: 0`, а правило
`.ui > * { pointer-events: auto }` делало его кликабельным на весь экран.
Ни один тап не работал, при этом игра выглядела совершенно нормально.

**Таймер блица шёл медленнее реального времени.** Остаток накапливался из
`deltaMS` тикера Pixi, а Pixi ограничивает `deltaMS` сверху (`Ticker.minFPS`,
по умолчанию 10 — то есть не больше 100 мс за кадр). На медленном рендере кадр
идёт 200–300 мс, лишнее отбрасывается, и шестьдесят «секунд» забега
растягивались в реальные девяносто. Для режима, который кормит недельный
лидерборд, это прямая несправедливость: у кого телефон слабее, у того забег
длиннее. Теперь остаток считается от метки времени окончания, а пауза
платформы продлевает её на своё время, чтобы реклама не съедала забег.
Порог `minFPS` заодно опущен до 4 — анимации ходов тоже перестали растягиваться
на слабых устройствах.

Обе ошибки не ловятся ни типами, ни юнит-тестами: код в обоих случаях
совершенно корректен сам по себе.

## Соответствие плану

Реализовано по плану, кроме трёх мест, где план не сходился с реальностью.

| Место | Что в плане | Что сделано и почему |
| --- | --- | --- |
| §6, генерация уровней | Обратные ходы от решённого состояния | Раздача + проверка солвером: обратное блуждание не умеет оставить заданное число пустых витрин (см. [выше](#почему-решаемость-обеспечивает-солвер-а-не-построение)) |
| §6, таблица сложности | 7–8 видов при 10–12 витринах и 1 свободной | Витрин = виды + свободные, то есть 8–9. Колонка «Витрин» в плане не сходится с двумя другими; ведущими взяты виды и свободные витрины — они и определяют сложность |
| §7, звук | OGG на аутсорсе | Синтез через WebAudio: ноль байт, ноль декодирования, высота тона отвечает на заполнение витрины |

Мелкие уточнения:

* **Один тап — одна фигурка**, как в §3. Перенос всей однородной серии за один
  тап (как в water sort) сделал бы `minMoves` из пака неприменимым.
* **Подсказка ищется в рантайме**, а не берётся из пака: игрок почти сразу
  уходит с оптимальной траектории, и заготовленный путь становится
  неприменим. IDA\* с бюджетом по времени; если бюджет исчерпан, отдаётся
  эвристически лучший ход — он всегда допустимый.
* **Сезон определяется датой** без сервера: отсчёт от фиксированной даты старта,
  поэтому у всех игроков один сезон в один день.
* **Ежедневный вызов** берётся из пака по номеру дня UTC — один уровень для всех
  без серверной части.

* **Скины витрин** ([`src/theme/skins.ts`](src/theme/skins.ts)) меняют
  **конструкцию**, а не палитру. Скин из четырёх переопределённых цветов даёт
  разницу «на пару оттенков»: купив его, игрок не может показать покупку даже
  себе. Поэтому у каждого скина своя сборка витрины — и своё скругление всего
  интерфейса:

  | Скин | Цена | Конструкция |
  | --- | --- | --- |
  | Сезонное | — | стеклянный шкаф, цвет по серии |
  | Ретро-полка | 450 монет | дерево, планка под каждым ярусом, ножки, мягкие углы |
  | Латунь | 800 монет | литая рама, заклёпки по углам, шильдик |
  | Аркада | 1200 монет | маркиза с лампами, боковые неонки, прямые углы, тумба |
  | Кристалл | 1800 монет | срезанные углы, диагональные грани |
  | Хром | за деньги | фаска с бликом по верхней кромке и тенью по нижней |

  Фон при этом остаётся сезонным, иначе смена сезона перестала бы читаться.
  Состояния витрины (выбрана, «сюда можно», закрыта) у всех скинов одинаковые:
  купленный скин не имеет права переучивать игрока. В магазине каждый скин
  показан миниатюрой (`skinChipSvg`) — по описанию конструкцию не выбрать.

  Лестница цен от 450 до 1800 — это и есть сток для валюты: без товара за
  монеты им некуда деваться, кроме блайнд-боксов, и накопления обесцениваются,
  едва серия собрана.

### Недельный пропуск отмеряет неделю без сервера

Пропуск обещает награду каждый день семь дней подряд, и обещание проверяемое:
покупка ставит **дату окончания** и сразу выдаёт первый из семи дней, остальные
шесть игрок забирает при входах, по одному в календарный день.

Хранится именно дата окончания, а не «осталось дней». Счётчик пришлось бы
уменьшать по какому-то событию — и игрок, не заходивший неделю, либо потерял бы
всё оплаченное, либо получил бы вечный пропуск, смотря где стоит декремент.
Дата не зависит от того, заходил игрок или нет, и своего сервера для этого не
нужно: `passUntil` лежит в облачном сохранении рядом с остальным прогрессом.

Сам день берётся не с устройства. Всё календарное — пропуск, награда за вход,
вызов дня, сезон — считает время через [`src/platform/clock.ts`](src/platform/clock.ts),
а тот спрашивает `ysdk.serverTime()`. На часах устройства недельный пропуск
растягивался бы на месяц, а ежедневная награда печаталась бы сколько угодно раз
за вечер: и дату, и часовой пояс игрок задаёт сам. День считается по UTC —
переключением пояса сутки тоже сдвигаются. Раньше отметка «вызов дня пройден»
жила по местной полуночи, а сам уровень менялся по UTC, и в Москве между
полуночью и тремя часами один и тот же вызов уходил в лидерборд дважды.

Повторная покупка **продлевает** действующий пропуск, а не начинает его заново:
иначе игрок, купивший второй пропуск на пятый день, потерял бы два оплаченных
дня — и был бы прав, потребовав возврат. Пока пропуск действует, магазин
показывает остаток дней, иначе купленный пропуск выглядел бы в точности как
некупленный.

Всё это закрыто тестами (`test/core.test.ts`, группа «Недельный пропуск»):
выдача не чаще раза в сутки, продление вместо обнуления, переживание
перезагрузки, истёкший пропуск. Первая же версия этих тестов поймала ошибку на
единицу — пропуск действовал восемь дней вместо семи.
